# 豆包对照实测结论（2026-08-30，用户手动操作 + 截图取证）

对照 `docs/没有完成的工作.md` 的三个对照需求，结论如下。

## 1. 悬浮球拖动效果

- **现象**：拖动豆包球时，球本体不动，在拖拽路径上显示一个**金色空心矩形框**作为落点指示（drag ghost 是位置占位框，不是球本身），松手后球落到框位置。
- **对照我们**：Promptly 是主进程 16ms 光标轮询、球实时跟手移动。
- **结论**：两种范式各有取舍——豆包的占位框方案实现更省（不需要逐帧移动窗口），但跟手感弱；我们的实时跟手更接近"物理拖拽"直觉。**不需要改**。可选的 v1.1 打磨：拖拽释放时加一个轻微的落定动画（scale 弹一下），成本低、手感增益明显。

## 2. 划词工具条定位与内容

- **定位**：工具条出现在选区**正上方**（不是下方），水平方向大致与选区居中对齐（截图红框显示工具条宽度略大于选区宽度）。此前附录 X 假设"默认下方、底部翻转上方"，豆包的默认方位是**上方优先**。
- **按钮组**：AI 搜索 / 复制 / 翻译 / 朗读 / 总结 / …（溢出菜单）。朗读(TTS)我们 v1 不做；按钮密度比我们高但靠 "…" 收纳。
- **对我们的修改**：附录 X 的定位算法把"默认在选区上方、空间不足时翻到下方"作为首选方位（与现有翻转逻辑互为镜像，改动小）。这与待办第一优先（定位复验）可以一并做。

## 3. 点击"AI 搜索"后的行为（体验分水岭的印证）

- **现象**：点击后不跳主窗，在选区附近原地弹出一个**锚定小卡**：
  1. 顶部是引用问句的 chip（选中文字回显，用户立刻确认"它理解对了"）；
  2. 中部流式输出（"搜索了 3 个关键词，参考 18 篇资料"的过程可见 → 感知等待成本低）;
  3. 底部自带**追问输入框**（+ / 对话 / 更多 / 语音），即迷你聊天窗就地展开。
- **对照我们**：三态工具条（动作→加载→结果 + Copy/Retry/在聊天中打开）方向一致，"结果进工具条"被豆包验证是正确路线；差异是豆包把追问能力也放进了原地卡片，而我们引导去主聊天窗。
- **结论**：v1 不改架构——"在聊天中打开"已覆盖追问闭环。记入 v1.1 候选：原地追问输入框。
- **可直接借鉴的两点（成本低，建议 v1 就做）**：
  1. **加载态回显选中文字**：我们加载态目前是纯 spinner，加一行截断的选区文字回显（单行 ellipsis），用户在等待时能确认问句，感知等待显著下降。
  2. **加载态展示过程信息**：哪怕只显示 provider 名/模型名（"DeepSeek 正在回复…"），也比空转强。

## 4. Z 序（上轮已实测，归档）

- 豆包球全局置顶（ZCode 全屏、资源管理器、OneDrive 之上均可见），与我们的 screen-saver 层级一致。**交接文档 §10 中"豆包的球会被全屏窗口遮挡"的说法有误，以本档为准。**
